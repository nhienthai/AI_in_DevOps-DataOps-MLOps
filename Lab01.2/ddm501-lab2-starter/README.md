# Lab 2: ML Pipeline & Experiment Tracking

A modular training pipeline for the movie rating model from Lab 1, with MLflow
experiment tracking, a model registry, and weekly retraining orchestrated by
Apache Airflow.

**Course:** DDM501 — Lab 2 (ML Pipeline & Experiment Tracking)

---

## What this does

```
             ┌──────────────┐
             │   Airflow    │  @weekly
             │  scheduler   │
             └──────┬───────┘
                    │
  load_data → preprocess → train → evaluate → decide_registration
                                                  │        │
                                       RMSE < 1.0 │        │ RMSE ≥ 1.0
                                                  ▼        ▼
                                          register_model  skip
                                                  │        │
                                                  └───┬────┘
                                                      ▼
                                                   cleanup
                    │
                    ▼  params, metrics, plots, model.pkl
             ┌──────────────┐
             │    MLflow    │  tracking + model registry
             └──────────────┘
```

- **Modular pipeline** — ingestion, preprocessing, training, evaluation and
  registry are separate importable stages, driven either by `run_pipeline.py`
  or by the Airflow DAG.
- **9 tracked experiments** across SVD / NMF / KNN, all scored on one shared
  test split so the numbers are comparable.
- **Model registry** with stage transitions; promoting a new version
  automatically archives the previous Production one.
- **35 pytest tests**, with the slow ones marked so a quick run stays fast.
- **Auto-generated experiment report** — see [experiment_report.md](experiment_report.md).

## Quick start

### 1. Install

```bash
cd ddm501-lab2-starter

python -m venv venv
source venv/bin/activate      # Linux/Mac
# venv\Scripts\activate       # Windows

pip install -r requirements.txt
```

### 2. Start MLflow

```bash
docker compose up -d mlflow
```

MLflow UI: **<http://localhost:5001>**

### 3. Run the pipeline

```bash
python -m pipeline.run_pipeline                              # defaults
python -m pipeline.run_pipeline --model-type svd --n-factors 50 --n-epochs 20
python -m pipeline.run_pipeline --register                   # also promote to Production
```

### 4. Run the experiment sweep

```bash
python -m experiments.run_experiments
```

Runs all 9 configurations from `EXPERIMENT_CONFIGS`, logs each to the
`hyperparameter-tuning` experiment, and writes `experiment_report.md`.

### 5. Start Airflow

```bash
docker compose up -d
```

Airflow UI: **<http://localhost:8080>** — login `admin` / `admin`.

```bash
docker compose ps                                             # all healthy?
docker exec airflow-scheduler airflow dags list
docker exec airflow-scheduler airflow dags unpause movie_rating_training
docker exec airflow-scheduler airflow dags trigger movie_rating_training
```

### 6. Run tests

```bash
pytest tests/ -v                      # all 35
pytest tests/ -v -m "not slow"        # skip the ones that need MLflow running
pytest tests/ -v --cov=pipeline --cov=experiments
```

## MLflow

### What each run records

| Kind | Contents |
|------|----------|
| Parameters | `model_type`, every hyperparameter, train-set shape (`n_train_users`, `n_train_items`, `n_train_ratings`) |
| Metrics | `rmse`, `mae`, `mse`, `mape`, `coverage`, `n_predictions`, `n_impossible`, `training_time_seconds` |
| Artifacts | `model/model_<type>_<run>.pkl`, `plots/prediction_distribution.png`, `plots/error_by_rating.png` |
| Tags | `stage` (`training` → `evaluated`), `algorithm`, `framework` |

Training and evaluation write to the **same run**: `train_model` returns a
`run_id` and `evaluate_model` reopens it. Otherwise the UI would show
parameters on one row and metrics on another, and sorting by RMSE would be
useless.

`coverage` is worth watching — it is the share of test pairs the model actually
scored. Surprise silently falls back to the global mean for cold-start pairs,
which flatters RMSE. All runs here report 1.000, so no score is inflated.

### Model registry

```bash
python -c "
import mlflow; mlflow.set_tracking_uri('http://localhost:5001')
from pipeline.registry import list_registered_models, get_production_model
print(list_registered_models())
print(get_production_model('movie-rating-model'))
"
```

`register_best_model()` finds the lowest-RMSE run, registers its artifact, and
transitions it to `Production` with `archive_existing_versions=True`, so exactly
one version is ever live. `load_registered_model()` downloads and unpickles
whatever is in Production — use it to confirm the registry holds a working
model rather than just a database row.

## Airflow DAG

`movie_rating_training`, schedule `@weekly`, `catchup=False`.

| Task | Does |
|------|------|
| `load_data` | Loads MovieLens, splits 80/20, pickles both to `/tmp` |
| `preprocess_data` | Validation + statistics; **raises** if validation fails |
| `train_model` | Trains SVD, logs the run, pushes `run_id` to XCom |
| `evaluate_model` | Scores the model, logs metrics onto the same run |
| `decide_registration` | Branch: RMSE < 1.0 → register, else skip |
| `register_model` | Promotes the best run to `Production` |
| `skip_registration` | No-op branch |
| `cleanup` | Deletes the `/tmp` working directory (`trigger_rule='none_failed'`) |

Data moves between tasks as pickles in a shared `/tmp` directory, with only the
path and small scalars going through XCom. XCom values are stored in the Airflow
metadata database, so pushing a 5 MB trainset through it would bloat the DB.

A failed validation stops the DAG rather than training anyway — a model trained
on data that failed its checks is worse than no model, because the run still
looks successful.

## Notes on the environment

These are deviations from the starter's pinned versions, each forced by a real
incompatibility rather than preference.

**Port 5001, not 5000.** On macOS the AirPlay Receiver holds port 5000, so the
MLflow container publishes `5001:5000`. Either use 5001 or turn AirPlay
Receiver off in System Settings → General → AirDrop & Handoff.

**MLflow runs in Docker, the client runs locally.** `mlflow==2.9.2`'s CLI calls
`importlib.metadata.entry_points().get(...)`, an API removed in Python 3.12, so
`mlflow server` cannot start under 3.12. The Python client is unaffected. Running
the server in its own container — which the lab's compose file already
prescribes — sidesteps this entirely.

**`setuptools<81`.** `mlflow==2.9.2` imports `pkg_resources`, which setuptools
removed in version 81.

**`scikit-surprise==1.1.4`, not 1.1.3.** 1.1.3 has no PEP 517 build metadata and
fails to build on Python 3.11+.

**`numpy<2`.** Surprise's Cython extension is compiled against the numpy 1.x ABI.

**Airflow is not in `requirements.txt`.** It ships inside its image, does not
support Python 3.12, and its constraint files conflict with the pins above.

**`apache/airflow:2.8.0-python3.11`.** The default 2.8.0 tag is built on Python
3.8, where `matplotlib==3.8.2` is unavailable (it needs ≥ 3.9).

**A valid Fernet key.** The starter's `your-fernet-key-here` is not valid base64
and breaks connection encryption. `docker-compose.yml` carries a generated demo
key — replace it for anything real:

```bash
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

**MLflow soft-deletes.** Deleting an experiment does not free its name. To
really remove one and reuse the name:

```bash
docker exec -e MLFLOW_TRACKING_URI=http://localhost:5000 mlflow-server \
  mlflow gc --backend-store-uri sqlite:////mlflow/mlflow.db
```

The `MLFLOW_TRACKING_URI` matters: without it `gc` cannot resolve the
`mlflow-artifacts:` scheme used by the proxied artifact store and fails.
